## 1. 目的と範囲

「以前噂になっていた銘柄を探し、確認できたその後を知る」までを短くする。

今回の実装範囲:
- 媒体名による複数選択、確認方法の区別、報道未確認・媒体未特定の扱い。
- 進捗と会社説明の分離、TOB成立と非公開化完了の区別。
- 一覧の統合、情報量・リンクの強弱の整理、詳細冒頭の整理。
- 出来事の期間検索、並び替え、全条件解除、公開条件のURL保持。
- 年月・号数・日付不明の入力と表示、管理画面、既存データの分類、必要なDB追加。

維持条件: 既存フォントファミリー・フォールバック順・継承・等幅指定、基本文字サイズと行高、Googleログイン、本人専用メモ・お気に入り・関心度・RLS、案件ID・URL、Cloudflare・ドメイン・SEO用の静的HTML。OpenAI API・X連携・株価チャートは追加しない。噂だけの銘柄から記事を作らない。

## 2. 初期画面と基本操作

トップページは次の順番にする。
1. 短いサービス説明。
2. 銘柄名・コード検索、媒体選択、段階切替。
3. 選択中条件、件数、並び替え、「条件をすべて解除」。
4. 一つの銘柄一覧。
5. 読み方・掲載基準への案内。

段階切替は「全段階／正式発表前／実施発表後／完了・終了」。全段階が初期値。これは段階だけを切り替える操作で、他の条件を解除しない。「すべて」という曖昧なボタン名は使わない。

お気に入りはログイン時に常時使える。期間・会社説明・詳細な進捗・関心度は「詳しい条件」に置く。折りたたんだ条件も選択中の表示に残す。

複数媒体の内部はOR、媒体・段階・検索語・期間・お気に入り等の間はAND。件数と一覧はcase_idで重複排除し、媒体数だけ行を増やさない。別案件が同一会社にある場合は案件を勝手に統合せず、「追跡対象○件」と数える。

## 3. 媒体分類

### 対象

その案件の非公開化・MBO・親子上場解消等の観測に関する報道・関連続報を対象とする。単なる決算記事や正式発表の転載だけでは、過去の噂の媒体として追加しない。分類対象である理由を保存する。

原報道を出した媒体と、閲覧した資料の発行者・配信サイトを分ける。Yahoo!掲載の記事を一律Yahoo!に分類しない。原報道と独自取材を伴う続報の両方がある場合は、それぞれの根拠に媒体を付ける。

### 公開分類

| 状態 | 定義 |
|---|---|
| 特定の媒体 | 報道の存在と媒体名を、閲覧可能な根拠で確認した |
| 媒体未特定 | 関連報道への言及は確認したが、媒体名を確認できない |
| 報道未確認 | 管理者が確認範囲と確認日を記録したうえで、関連報道の存在を確認できていない |
| 分類確認中 | 移行・入力途中。上記のどれかに自動で置き換えない |

報道未確認は「報道が存在しない」という意味ではない。記事が0件、出来事が0件、source_nameが空というだけで自動分類しない。分類確認中は媒体選択とは別のデータ整備状態であり、初回公開切替では既存の公開案件を全件分類する。

媒体未特定の根拠と、特定媒体の根拠は同一案件に共存できる。報道未確認は、公開済みの確認根拠がある案件と両立しない。新たに根拠を承認した際に同時に更新する。

### 選択UI

「媒体を選ぶ」内にチェックボックスを置く。Mergermarket、日本経済新聞、選択、Bloombergなどの登録媒体を表示する。表記ゆれは別選択肢にしない。その他の媒体も正式名を登録し、入口では「その他」から開けるようにする。

媒体の横の件数は、媒体条件を外して他の条件だけを適用した場合の該当案件数。一案件が複数媒体に属するため、媒体別件数の合計は総件数と一致しなくてよい。現在選択中の0件の媒体を隠さない。

「報道未確認」を選ぶと媒体の選択を解除し、特定媒体・媒体未特定を選ぶと「報道未確認」を解除する。選択中の条件を文字で表示する。

一覧では媒体を最大2つ＋「ほか○媒体」で表示し、残りをその場で開ける。確認方法は媒体に対応付けて表示し、全媒体を読了したように見せない。

### 確認方法と原文の閲覧範囲

確認方法は「原報道を直接確認／会社開示で言及を確認／二次報道で言及を確認」。原文の閲覧範囲は「本文確認／公開部分のみ／原文未閲覧」。別項目として保持する。

例: 日本MDM → Mergermarket → 会社開示で言及を確認 → 原文未閲覧。
会社開示が媒体を名指ししていなければ、説明文の推測でMergermarketを選ばず媒体未特定とする。

各根拠には、根拠のタイトル・URL・確認日・確認できた範囲・原報道の日付または不明・関連イベントを記録する。報道の事実関係に後日否定が出ても、報道が存在した記録は残して否定イベントを関連付ける。媒体の取り違え自体を訂正する場合は訂正理由を残す。

## 4. 進捗と会社説明

### 主タグ: 確認できた到達点

| 内部値案 | 公開表示 | 段階切替 |
|---|---|---|
| pre_announcement | 正式発表前 | 正式発表前 |
| announced | 実施発表 | 実施発表後 |
| offer_open | TOB開始 | 実施発表後 |
| offer_succeeded | TOB成立 | 実施発表後 |
| delisted | 上場廃止 | 完了・終了 |
| privatized | 非公開化完了 | 完了・終了 |
| consideration_ended | 検討・協議終了 | 完了・終了 |
| withdrawn | 撤回 | 完了・終了 |
| failed | 不成立 | 完了・終了 |

「実施発表」は実施の公式発表を確認した段階で、TOB開始予定を含む。単なる提案受領・検討説明・観測報道ではこの段階にしない。「TOB開始」は開始を公表した資料が必要。条件付きの開始予定日が来ても進めない。

「上場廃止」と「非公開化完了」は別であり、上場廃止から自動で完了へ進めない。TOBを行わない非公開化にも対応する。これは進捗の一本道ではなく、確認できた事実の区分。

状態の根拠イベント・基準日・短い補足を管理者が選び、公開承認する。イベント名の文字列や一番新しいイベントだけから状態を決めない。誤分類なら訂正可能にする。古い交渉終了の後に別の買い手で進展する場合は、現在の取引の状態を選び、過去の終了イベントを消さない。

### 会社説明の補助表示

会社説明は主状態から独立し、「日付・発言主体・内容」を表示する。内容は既存comment_tagsを活用し、「提案受領」「非公開化の検討に言及」「選択肢を検討」「協議に言及」「決定事実なし」「検討を否定」「報道内容を否定」「回答を差し控え」などを区別する。

一覧に採用する説明を管理者が明示的に選ぶ。親会社・対象会社・買付者が異なる説明をしている場合、別主体の回答を上書きしない。矛盾がある場合は「会社説明に相違あり」の短い注記と双方の根拠を残す。

過去の説明を「現在も検討中」に言い換えない。否定は「9/1 対象会社が検討を否定」のように日付と範囲を示す。否定だけで追跡を終了しない。「決定事実なし」「会社の発表ではない」は検討の否定と分ける。

詳細条件の「会社説明」は一覧で採用した説明に対して検索する。説明は過去時点の発言であることをUIに明記。過去すべての肯定的コメントを対象にする現行の主要ボタンは廃止し、提案受領を「検討を認めた」に一括変換しない。

色は進捗の大分類に使い、文言でも判別できるようにする。報道回数による強弱・実現確率のスコアは使わない。長期未進展は主タグにせず、最終公表日と確認日を示す。

## 5. 一覧と詳細の表示

PCでは「銘柄／きっかけ・媒体／到達点／直近の公表情報」の4列。お気に入りは銘柄欄にまとめる。モバイルは同じ順のカード。一覧で横スクロールを要求しない。

銘柄名は濃い文字と詳細への矢印、ホバー・フォーカス時の下線でリンクを明示する。訪問済み色が文字の強弱を崩さないよう一覧内で指定する。行全体をリンクにせず、星・詳細・出来事・外部リンクを独立して操作できるようにする。

一覧には編集した短い追跡理由・状況要約を使う。目安は各40〜70文字で、原文を機械的に切らない。重要な否定・原文未閲覧・成立未確認などを省略しない。字数を超える必要がある場合は折り返しを許容する。長い調査メモは詳細へ。

一覧の外部リンクは「株探チャート ↗」を直接表示する。詳細には株探チャート・株探業績・Yahoo!ファイナンスの3つを維持する。上場廃止銘柄はリンク先の情報が終了する可能性を補足し、外部サイトの有無を非公開化完了の根拠にしない。

詳細の冒頭:
1. 社名・コード・主タグ・お気に入り。
2. 状況を説明する短い一文、根拠日、重要な未確認事項。
3. 関連媒体と確認方法、追跡のきっかけ。
4. 「経過」「関連記事」「自分のメモ」への導線、外部リンク。
5. 経過タイムライン。長い検証記録は開閉可能だが、重要な注記は閉じ込めない。

既存の出来事アンカーとメモのcase_idを維持。会社ページ・記事の関連記事・マイページの状態表示も共通定義を使い、トップだけ新分類にしない。

## 6. 日付・期間・並び順

公表日、予定日、号数、サイト登録日、最終確認日、編集更新日を別の情報として扱う。

### 精度

- 日時: 確認できた日時を保存・表示。
- 日付のみ: 日付を表示。保存上の時刻を実際の発表時刻として表示しない。
- 公表年月のみ: 公表月が確認できた場合だけ使用。特定の日を公開しない。
- 号数のみ: 「2026年1月号」。号数の月は発行月・公表月と同一とは限らない。
- 不明: 「公表日未確認」。登録日時で穴埋めしない。

タイムラインは年月グループ内で、日付確認済みを時系列表示する。号数しかない記録は該当する号の年月グループに「号数による参考配置」として別枠で表示し、月内の正確な順序を示さない。年月も不明な記録は「日付未確認の記録」に分離する。任意のsort_atを公表日へ流用しない。

### 期間検索

初期値は期間指定なし。「直近12か月」「年」「開始日〜終了日」を選択可能。JSTの日付で両端を含む。直近12か月は検索時の当日を上限とし、12か月前の翌日を下限とする。閏日等で存在しない日は月末に合わせ、UIに実際の範囲を表示する。

期間内に公表された出来事が1件以上あれば案件を表示する。過去の会社回答も対象。予定日が期間内というだけでは該当させない。

公表年月のみの記録は月の範囲が重なる場合に含め、「月単位の一致」を示す。号数だけ・完全不明は通常の公表期間検索には含めず、除外された記録があることを表示する。詳細条件「号数の年月も含める」を選ぶと参考一致として含め、実際の公表日とは区別する。

媒体条件は案件の全経過、期間条件は出来事に適用する。例: 5月にMergermarket報道、9月にTOB成立なら「Mergermarket＋9月」で表示する。画面にも「その媒体に関連し、期間内に出来事のある案件」と説明する。「選んだ媒体がその期間に報道した」という検索は初期実装に含めない。

### 並び順

既定は「公表情報が新しい順」。日付・公表年月を確認できた出来事から選ぶ。号数だけを新しい公表情報として扱わない。公表年月のみは月初を比較上の下限として用い、実際の日付として表示しない。同順位は証券コード・case_idで安定化する。

比較できる公表情報のない案件は同じ一覧の後方に置き、追跡登録日の新しい順。「公表日未確認／追跡登録○日」と明示する。これにより新規の噂だけの銘柄を公表情報の新着と混同しない。新規銘柄は別の「追跡登録が新しい順」で探せる。

ほかに「サイト更新が新しい順」「証券コード順」を用意する。本文訂正はサイト更新順には影響するが、公表情報順には影響しない。日付訂正は公表情報順にも反映する。出来事のない銘柄の登録日は後からの編集日で変えない。

期間検索中は、一覧の最新情報は全経過の最新を維持し、「期間内: 2026/05/14 会社回答」のように該当した出来事への補助リンクを表示する。過去期間で検索したために現在の状態が昔の状態へ戻ったようには見せない。

## 7. 検索条件・アクセシビリティ・SEO

- 公開条件はURLのクエリで再現する。媒体IDを複数指定でき、旧URL・不正値・未知IDで例外を起こさない。認識できない条件は無視した旨を表示し、修正可能にする。
- 検索文字はNFKC正規化・前後空白除去・英字大小文字の統一。表示名は改変せず、英字入り証券コードを数値化しない。
- 選択中の条件を個別解除可能にする。「条件をすべて解除」は検索、媒体、期間、段階、会社説明、お気に入り、関心度を解除し、既定の並びに戻す。お気に入り登録そのものは削除しない。
- 検索語入力では履歴を細切れに増やさず、離散的な条件変更は戻る・進むで復元可能にする。詳細へ進んで戻った際も条件を復元する。
- お気に入り・関心度・メモ内容・ユーザーIDは共有URLや公開HTMLに含めない。本人用条件はタブ内の状態で保持し、ログアウト時に解除する。
- キーボード、チェックボックスのラベル、選択状態、明瞭なフォーカス、結果件数の通知、0件時の解除導線を用意する。色だけ・ホバーだけに依存しない。
- JavaScriptなしでも公開一覧と詳細を閲覧できる。絞り込みにはJavaScriptが必要な旨を示す。
- 本文、媒体の根拠、出典、関連記事は静的HTMLに出す。既存canonical・sitemap・URL・見出しの意味を維持し、フィルターの組合せごとのページを大量生成しない。クエリ付き一覧のcanonicalはベースの一覧とする。検索順位の維持を保証するとは記載しない。

## 8. データ・管理画面・承認

以下は責務を具体化した論理モデル。物理テーブル名と制約は実装開始時の実DB・未マージPR確認後に確定する。

| 単位 | 必要な項目・関係 |
|---|---|
| 媒体辞書 | 安定ID、表示名、別名、有効状態。別名も重複を防ぐ |
| 報道の確認根拠 | case_id、媒体IDまたは媒体不明、関連イベント、原報道の識別情報、確認した出典名・URL、確認方法、閲覧範囲、公表日精度、確認日、対象に含める理由、訂正履歴 |
| 案件の公開表示 | case_id、分類確認状態、確認範囲、主進捗と根拠イベント、採用する会社説明、一覧用要約、重要な注記、最終確認日 |
| 出来事の日付情報 | event_id、公表日精度、公表年月、号数ラベル・号数年月。既存日時・metadata等と整合させる |

案件に媒体タグを手入力して、別途イベントにも媒体を手入力する二重管理はしない。公開案件の媒体一覧は承認済みの確認根拠から集約する。一つの出来事に複数媒体の確認根拠を持てるようにする。

編集途中の新しい分類・要約・確認根拠は下書きとして保存し、公開版と分離する。公開承認は関連項目を一つのトランザクションで検証・反映する。管理者が編集中に別の更新で再ビルドされても、下書きを公開しない。競合する編集は版番号などで検知し、後勝ちで無言上書きしない。

新しい日付精度・号数の編集もこの承認対象に含める。旧公開画面が読む日時を下書き保存時に直接書き換えない。新画面の公開切替前に、旧画面が解釈できない精度値を公開用の既存列へ投入しない。旧管理画面を併用できる期間と編集制限も移行手順で明示し、互換値の同期漏れを防ぐ。

公開条件: 根拠URLと確認日、分類理由、許容値、文字数、イベントの案件所属・公開状態、報道未確認との排他、主状態の根拠を検証する。根拠が非公開になった場合は、参照する公開分類の扱いも同時に変更する。無効な参照を黙って無視して確定表示を続けない。これらの整合を公開処理とビルドで確認する。

新しいテーブル・RPCは管理者限定で編集し、公開ビルドは承認済み情報だけを読む。一般ユーザー用RLSは変更しない。公開サイトから直接DBを読む構成を追加しない。

管理画面は「媒体・根拠を登録」「到達点・会社説明を選択」「一覧のプレビュー」「公開版との差分確認」「承認」「公開処理」の順にする。保存済み、承認済み・反映待ち、公開反映済み、公開失敗を区別する。原文未閲覧のまま根拠付き分類を登録でき、閲覧したことにする入力を求めない。

旧statusは当面残す。新しい公開状態を主とし、旧状態は旧画面・切り戻し用の互換値とする。新画面から保存する際は必要な互換値も同時更新し、2系統を独立編集しない。旧completedを一括で非公開化完了へ置き換えない。旧状態だけの未移行データは「分類確認中」とし、初回切替は公開全件の移行完了を条件にする。

日付列はPR #8の補助列が存在するDBも考慮する。精度の解釈は一つの関数・管理入力に集約し、既存列と新規列の無言の食い違いを作らない。適用済みSQLは編集しない。

## 9. 既存データの移行と確認例

既存の公開11案件・27出来事・2記事を基準に、実装時には増減を再確認する。ID・slug・メモとの関連は維持する。

- 日本MDM・CEHD: 会社開示を根拠にMergermarketへの関連を登録する候補。原文未閲覧を維持。
- イーソル: 会社開示で日経報道への言及を確認した分類とし、日経検索で出るようにする。
- 電通総研: 選択・日経などの根拠を分ける。1月号は号数扱い。株探の記事は独自の関連報道か転載・相場解説かを確認して分類する。
- ニッコンHD: 確認した二次報道と原報道元の関係を登録。旧説明文のMergermarketという語だけで分類しない。
- スクウェア・エニックスHD: 報道への関連と会社の否定を両立させる。否定で案件終了へ移さない。
- CEHD: TOB成立と上場廃止未確認を分離する。
- 養命酒製造: 過去の交渉終了が現在の最終状態を上書きしない。
- 豆蔵・ホギメディカル: 旧completedからの移行時に、上場廃止と株式取得完了の根拠をそれぞれ確認する。
- 小林製薬・壱番屋: 提案受領・親会社による選択肢の検討を区別し、「検討を認めた」に一括変換しない。

これは移行時の確認項目で、媒体・状態の最終投入表ではない。直前に根拠と最新公開内容を再照合し、確認できない項目は確定値で埋めない。報道未確認・複数主体の回答矛盾・完全日付不明・同一会社の複数案件は、非公開テストデータでも検証する。

## 10. 実装の分割と公開手順

1. **見本と分類表**: 既存フォントの一覧・詳細の見本、全公開案件の移行表、文言を準備。仕様矛盾が判明した場合は実装を止めて管理者に質問する。
2. **追加DBと管理側**: 実DB・PR #8・最新mainを確認し、新規マイグレーション、承認処理、入力・プレビューを実装。公開画面はまだ旧版のまま動ける状態を保つ。
3. **分類・日付・検索の共通処理**: 根拠からの媒体集約、進捗、期間判定、安定ソート、URL条件を独立して検証する。
4. **公開画面**: トップ、詳細、会社ページ、マイページの関連表示を更新。認証やメモの保存処理は維持し、共通の表示定義を使う。
5. **移行・受入確認**: 下書きで全公開案件を分類。プレビューで実データ相当の表示を照合し、承認版を用意する。新画面の公開は分類がそろってから。
6. **本番反映**: 既存のCloudflare公開前DB自動適用を使用。ビルド・分類整合の失敗時は前の公開サイトを維持する。本番で件数・検索・詳細・認証・保存を確認。

SQLを管理者が毎回手貼りする運用には戻さない。追加型の変更と既存デプロイへの切り戻しを基本にし、DB全体を巻き戻さない。新規の資格情報や権限拡大が必要になった場合のみ、内容を示して別途確認する。

## 11. 受入条件

| ID | 必ず確認すること |
|---|---|
| M1 | 日経でイーソルと電通総研が検索でき、確認方法が正しく表示される |
| M2 | 複数媒体OR・他条件ANDが正しく、同一案件が重複しない |
| M3 | 原文未閲覧、媒体未特定、報道未確認、分類確認中を取り違えない |
| M4 | 未検証の文章中の媒体名・単なる配信先で自動分類しない |
| S1 | TOB成立・上場廃止・非公開化完了が区別され、予定日では状態が進まない |
| S2 | 会社の否定に主体・日付・範囲があり、未決定と否定を混同しない |
| S3 | 過去の交渉終了や否定が後の確認済み進展を隠さない |
| D1 | 日付・年月・号数・不明を正しく表示し、公表日時を捏造しない |
| D2 | JST境界・閏日・月末・年跨ぎ・期間端・日付不明・予定日を期間検索で検証 |
| D3 | 本文修正で公表情報順が変わらず、日付訂正なら変わる。順序が安定する |
| F1 | 全条件解除、0件、複数媒体、戻る・進む、再読み込み、詳細から戻るが動く |
| F2 | 個人条件・メモが共有URL・公開生成物に混入しない |
| U1 | PC・狭い画面で一覧が読め、キーボードでフィルターとリンクと星を個別操作できる |
| U2 | フォント指定・順序・継承を差分と実画面で維持確認し、重要な否定を切り落とさない |
| P1 | 保存した下書きが別の再ビルドで公開されず、承認・反映の状態を区別できる |
| P2 | 公開根拠の不正参照・他案件参照・競合更新・非管理者の編集を拒否する |
| R1 | Googleログイン、メモ保存・編集・再読込・再ログイン後の保持、お気に入り・関心度を確認 |
| R2 | 他ユーザーへのアクセス拒否、既存ID・URL・canonical・sitemap・公開記事2本の保持を確認 |
| R3 | 旧DBとの追加互換性・旧画面への切り戻し・マイグレーション再実行時の扱いを検証 |

チェックは既存npm test・npm run check・ビルドに加え、意味のある検索・日付・承認・DB権限テストとブラウザーの実操作を使う。単にテスト件数が増えたことを完了条件にしない。現行データ件数は実装開始時の差分も考慮する。
