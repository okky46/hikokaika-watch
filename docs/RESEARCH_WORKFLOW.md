# APIを使わない調査・ドラフト作成

OpenAI API、X連携、有料データ契約は追加しない。ChatGPT／Codexで調査してドラフトを作り、管理者が内容を確認する。既存のニュース収集Actionは候補収集だけを継続する。

## 記事・文章の執筆と推敲

2026-10-02以降、記事・要約・出来事の説明・追跡理由・画面の案内文には、ユーザーが毎回指定しなくても [yomiyasu](https://github.com/nanaism/yomiyasu) を使う。この端末の `~/.codex/skills/yomiyasu` に導入済みで、今回限りの利用にはしない。チャットを切り替えた担当者は [AGENTS.md](../AGENTS.md) からこの方針を確認する。

執筆前に確認済みの資料を整理し、誰が、いつ、何をしたかを明確にする。要点から書き、段落ごとに一つの話題を扱う。長い文は意味のまとまりで分け、重複した説明や抽象的な前置きを減らす。専門用語は必要なものを残し、読者が理解できる言葉で説明する。

推敲前に、利用環境のyomiyasuの `SKILL.md` と必要な参照文書を読む。原文の主張・比重・断定の強さ・文の働きを保持する。会社名・証券コード・日付・数値・出典と、情報を確認できた範囲も変えない。噂、報道、会社の説明、確認済みの事実、筆者の解釈、未確認事項を区別する。短くするために必要な条件や否定を削らず、資料で確認できない主語・原因・結論を補わない。引用文は原文を保ち、要約する場合は引用と区別する。

保存時はスキルのリンターを実行し、書き直した文章は変更前後を比較する。検出結果を見直し候補として確認し、意味に必要な表現は保持する。文長や点数を整えるためだけに、自然な文章を書き換えない。yomiyasuによる文章の検査と、出典・日付・事実の照合は別々に行う。公開前の管理者確認と掲載手順も継続する。

## 対象と探索記録

初回の基準日例: 2026-09-29。過去12か月: 2025-09-29〜2026-09-29（後日調査する場合は更新）。
月別に、非公開化・MBO・親子上場解消・戦略的選択肢・資本政策などを調べ、検索条件／確認日／企業コード／既存案件URL／出典／当時の日付を記録する。検索結果を網羅的な一覧とみなさない。

1. 既存会社・案件をコードで検索する。同じ追跡の続報は既存の案件へ追加する。再燃など別案件にする場合は理由を記録する。
2. 噂・市場観測だけの銘柄は「追跡銘柄」として整理する。追跡理由に、確認した範囲と未確認である点を書く。**記事は作らない**。
3. 会社のIR・適時開示・確認できた報道があれば出来事を整理する。会社が「決定なし」と述べただけで「検討なし」に置き換えない。否定・終了も同じ経過に残す。
4. 公表資料を整理する独立記事が必要なら、以下のJSONを作る。管理者が内容・リンク・日付を確認し、管理画面のドラフト取込に貼り付ける。
5. 取込は入力欄への反映だけ。下書き保存 → 公開承認 → 再ビルド → 反映確認を行う。

有料記事を購読していない前提で調査する。公開見出しや会社コメントで確認できる部分を超えて本文を推測しない。市場の聞き伝えを「Mergermarket／選択が報じた」と断定しない。2026-10-03のユーザー指示に従い、Mergermarket公式Xの公開投稿は手動で確認し、出典リンクとして掲載できる。Xの自動取得・埋め込み・API連携は追加しない。
株価・出来高の動きは非公開化やインサイダー取引の証明として扱わない。免責や疑問形だけで法的安全が保証されるという前提にしない。

## 追跡対象のドラフト項目

会社名、証券コード（文字列）、案件タイトル、既存案件との関係、URL用slug、追跡理由、追跡開始日、最終確認日、確認状況・未確認事項を用意する。管理画面「追跡銘柄」の対応欄へ入力する。古い日付が不明なら空欄にする。
記事も報道イベントもゼロでよい。報道日を登録日・収集日で代用しない。

## 記事取込JSON（すべて架空の例）

```json
{
  "version": 1,
  "kind": "article",
  "slug": "demo-capital-policy-note",
  "company_codes": ["130A", "245B"],
  "content": {
    "title": "資本政策の公表資料を整理する（架空の例）",
    "summary": "確認できた方針と未確認の実施方法を分ける。",
    "confirmed_facts": "架空の会社が資本関係の見直しを説明した。",
    "body": "公表資料を確認した順序や経緯。HTMLやMarkdownではなくプレーンテキスト。",
    "interpretation": "資本関係の見直しだけで非公開化の決定とは読めない。",
    "unknowns": "方法・時期・条件は未確認。",
    "checked_on": "2026-09-29",
    "correction_note": "",
    "sources": [
      {"name": "会社IR（架空の例）", "url": "https://example.com/ir/", "published_on": "2026-09-01", "checked_on": "2026-09-29"}
    ]
  }
}
```

会社はコードで照合する。未登録なら先に会社タブで登録する。関連付けは会社単位で、その会社の複数の追跡ページにも記事が出る。下書きの関連銘柄を変更しても公開承認前の公開版は変わらない。
出典の公表日不明は `""`、確認日は必須。公開にはタイトル、要約、確認できた事実、確認日、出典1件以上が必要。これらは形式チェックであり、内容が正しいことの自動判定ではない。
同じslugの再取込は新規作成せず、一覧から既存記事を編集する。公開後のslugは固定。非公開に戻した後も同じURLで再公開できる。
訂正は「訂正履歴」欄に日付・変更点・理由を追記し、以前の履歴を残す。取込JSONに個人メモ、認証情報、内部情報を含めない。

## 初回候補集から登録へ進むとき

- 未承認の原稿は管理者向けローカル成果物に置く。公開リポジトリ・PRへの掲載も外部公開に当たるため、進捗だけをリポジトリに記録する。
- 新規の追跡開始日は当サイトが追跡を始める日。過去の報道日は出来事として保存し、初報・会社回答・資料掲載・追跡開始を区別する。最初の噂の日が不明なら推測しない。
- 会社の検討否定は当時の発表主体・範囲を保持する。後のTOBだけで過去の回答を虚偽と評価しない。
- 「TOB開始予定」「TOB実施中」「TOB成立」「上場廃止済み」を本文で区別する。決済予定日や上場廃止予定日が到来しただけで完了扱いにしない。
- 原資料を取得できなかった候補は保留にし、二次報道しか確認できないものは出典と確認範囲を明記する。検索で続報を見つけられなかったことは、続報が存在しないことを意味しない。
- 銘柄候補のレビューJSONは記事取込JSONと別物。SQLや一括登録へそのまま流さず、承認対象の差分だけを管理画面へ反映する。既存案件のURL・ID・公開状態を一括上書きしない。

- 日付だけ判明している出来事は管理画面の「日付のみ判明」を使う。既存metadataに精度を記録し、保存上のJST日付基準を実際の発表時刻として表示しない。
- 一括した画面操作の成功表示だけで掲載完了と判断しない。保存後の対象銘柄・出来事件数・公開状態・会社コメント分類と、再ビルド後の公開本文・日付・出典を原稿と照合する。入力が残っている場合は新規フォームのクリアを確認してから続ける。

## 時系列を補う調査とMergermarket公式X

会社IRと適時開示を遡り、現在の印が変わる出来事を確認する。会社の検討・協議への言及、検討否定・報道否定、TOB等の正式発表、実際のTOB開始、条件や期間の変更、成立、不成立・撤回・検討終了、上場廃止・非公開化完了を区別する。現在の色の濃淡は管理者の別の評価なので、出来事の追加から自動変更しない。

Mergermarket公式Xが「以前に報じた」と説明する投稿も調査対象にする。投稿の本文と投稿日時を公式ページで確認し、元の報道日・内容と分けて記録する。正式発表後の投稿でも、元の初報日が分かれば遡って追加する。投稿の公開部分を読んだことを有料記事本文の閲覧に置き換えない。報道日が特定できなければ推測せず、その範囲を残す。

媒体マスターのMergermarketへの関連付けを必須にする。公式X、会社開示による報道への言及など、媒体と銘柄の関係を確認できる根拠を残す。原記事のアクセス範囲と確認方法も保存し、公開後にタグと媒体検索を照合する。媒体が不明な噂は確認済み報道へ昇格させない。

発表日、予定日、実施日を別々に扱う。TOB開始は開始後の変更・届出・結果等でも確認できる。決済や上場廃止の予定日が到来したことだけでは完了と判断しない。公開中の出来事は重複させず、既存IDを保持して必要な説明・日付・出典を補う。検索や公式Xの確認範囲を残し、全件を網羅したとは表示しない。
