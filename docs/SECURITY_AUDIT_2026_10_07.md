# 本番サイト・DBのセキュリティ点検（2026-10-07）

## 対象と確認方法

対象は `https://hikokaika.com/`、既存Cloudflare Pages、Supabaseの公開API・DB権限、公開成果物と依存関係。開始時の本番はCloudflareでmain `49338f6`、デプロイ `b61fe0ac-1c5b-4992-8686-272dc1b07d33` と確認した。DBの適用履歴は0018まで16件。未マージPR #92はUI改修で、SQL追加はなかった。元の作業ディレクトリの未コミット変更を保持し、専用worktree・ブランチ `codex-security-audit` で作業した。既存リモートのブランチ名との衝突を避けてこの名前を使用する。

本番では管理画面・APIの未認証アクセス、匿名APIの可視件数、偽造JWTの拒否、公開JSの秘密情報を確認した。DB管理画面ではテーブル権限・RLS・ポリシー・関数定義・適用履歴だけを読んだ。個人メモの本文は取得せず、本番への攻撃用書き込み・全件削除・負荷試験は行っていない。ユーザー間の攻撃と保存操作は、全マイグレーションを適用した隔離PostgreSQLで検証した。

## 発見した問題と修正

| 項目 | 確認した状態 | 修正 |
| --- | --- | --- |
| 過剰なDB権限 | 16テーブルすべてRLS有効だが、旧11テーブルに匿名ロールの権限と認証ロールのTRUNCATE権限が残る。TRUNCATEはRLSの対象外 | SQL0019で匿名の全テーブル権限、認証ロールのTRUNCATE・REFERENCES・TRIGGERを削除。管理者一覧への直接アクセスと監査履歴の直接変更も削除 |
| 関数の公開範囲 | `is_admin()` と監査用トリガー関数がPUBLIC経由で匿名にも実行可能。匿名の管理者判定結果はfalse | PUBLICからも取り消し、`is_admin()` は認証ロール・service_roleだけに限定。トリガー関数はAPIから直接呼べないようにする |
| 関数の検索先 | `set_updated_at()` に固定search_pathがない | `pg_catalog, public, pg_temp` を設定 |
| 将来の権限再拡大 | 新規テーブル・関数が既定権限でAPIへ公開される余地 | 匿名・認証ロールの自動付与を停止。新規オブジェクトには必要な権限を明示する。PUBLICの関数実行はグローバル既定権限からも取り消す |
| 既知の依存脆弱性 | Astro 5系と関連依存にnpm監査の指摘あり | Astro 7.3.6と互換性のある修正版へ更新。更新後のnpm監査は0件 |
| スクリプト実行制限 | CSP未設定 | Astroが生成するハッシュで実行スクリプトを限定し、インラインイベント属性とevalを許可しない。object・base・外部フォーム送信を制限し、HTTPヘッダーで埋め込みを禁止 |
| ビルド認証の保存 | Cloudflareのservice_roleキーが通常のテキスト変数 | 値と権限を変更せずシークレット変数へ切り替え、暗号化済み表示と本番ビルド成功を確認 |

TRUNCATE権限の存在は、公開REST APIからDB全体を削除できることを意味しない。今回、その実行経路は確認していない。RLSが守られていても不要な強い権限を残さないために取り消す。依存の重大な指摘についても、静的配信で使用していないSSR・画像最適化等の経路があり、本番でコード実行を実証したとは扱わない。

自動デプロイは0019適用後のRLS・匿名権限・認証ロールの全件削除権限・トリガー呼び出し権限を更新前後に検査する。保護条件を破るSQLはトランザクションごと戻して公開を停止する。ビルド後にもCSP、実際のインラインスクリプトのハッシュ、秘密情報の非出力を検査する。依存のNode.js必要条件に合わせ、CIとCloudflareのビルドを公式22系保守版22.23.3へ更新する。Linuxで不足した任意依存の記録は、空の作業場所でlockfileを再生成して解消する。

## 確認できた保護と回帰検証

- 本番の `/admin`、`/admin/`、`/admin/index.html`、`/api/analytics` は未認証でCloudflare Accessへ転送された。標準pages.devドメインの管理画面と統計APIも同様。`.env` と `.git/config` は404。
- 匿名APIの個人メモ・お気に入り・管理データは、本文を読まない件数照合で可視0件。公開版読取RPCは401、署名のないservice_role偽造JWTも401だった。公開JSにあったJWTはanonで、service_roleや秘密トークンの漏出は検出しなかった。
- 本人メモ・お気に入りの保存、読取、編集、削除が隔離DBで成功。他人の読取・変更・削除・所有者の付け替え・偽装登録、管理者への自己昇格、非管理者の管理RPC、TRUNCATEは拒否された。管理者も他人のメモを読めない。
- 管理者による会社編集とトリガーによる監査履歴記録、service_roleによる公開版読取は成功。監査履歴の直接削除は拒否された。既存のGoogleログイン設定、認証関数の本体、本人限定RLSは変更していない。
- 既存を含む180テスト、追加した成果物検査の1テスト、型検査、サンプル33ページのCloudflareビルド、既存の成果物検査が成功。型検査はエラー0・警告0で、既存外部スクリプトのヒント2件。フォント指定に変更なし。

## 二段階認証と残る範囲

管理者判定は管理者一覧への所属を確認し、DB側でaal2を必須にしていない。確認時に登録済みTOTPは0件。管理者のSupabaseセッションが盗まれた場合、Cloudflare Accessを経由せずDBの管理APIを使用されるリスクが残る。

ユーザーからCodexによるDB変更・案件登録への影響について質問があったため、MFA必須化は保留した。構造変更の専用デプロイ認証は引き続き使用できる。管理画面での登録にMFAを必須化すると、再認証時に本人のコード入力が必要になる。運用を決めて登録が完了するまでは、認証関数を変更しない。

本番の既存ログイン済みアカウントで全体メモを一時保存し、再読込後の一致、元の内容への復元と再読込後の一致を確認した。ブラウザーのエラーは0件だった。新規Googleログイン、別の実ユーザーによる攻撃、銘柄別メモ・お気に入りの本番書き込みは今回未実施で、隔離DBの役割別検証と区別する。DB管理サービス自身の内部実装、全アカウントの認証情報、外部広告スクリプト、DoS耐性は、この点検だけで安全性を保証していない。

Security Advisorを再実行するとエラー0、警告10、提案2だった。警告9件は認証ユーザーから呼べるSECURITY DEFINER関数で、管理者判定・管理RPCの既存仕様に当たる。各管理RPCの管理者検査を維持する。残る1件は漏えい済みパスワードの拒否が未有効という警告。メール認証は有効、メール確認は必須、匿名サインインは無効、Google認証は有効と読取確認した。漏えい済みパスワード拒否は[SupabaseのPro以上の機能](https://supabase.com/docs/guides/auth/password-security)で、契約変更は行っていない。アプリのログイン導線はGoogleで、メール認証を廃止する仕様判断も今回行っていない。
