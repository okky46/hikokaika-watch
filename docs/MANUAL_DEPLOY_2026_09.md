# 今回の改修を本番へ反映する手順

本書はコード改修後の作業用。**本番Supabase・Cloudflare・DNS・OAuthは、この改修作業では変更していない。**
コードのマージだけではDB変更は実行されない。SQLを先に適用し、その後に新コードをデプロイする。

## 1. 変更前に記録する

- Cloudflare Pagesの現在の正常なProductionデプロイIDを控える。切り戻しに使う。
- 現在のSupabaseプロジェクト、Cloudflareプロジェクト、環境変数名を確認する。値をGitHubやチャットへ貼らない。
- Supabaseで公開データ・管理設定を含むバックアップ／エクスポートと復元方法を確認する。個人メモの保持は必須ではないが、今回のSQLは削除しない。
- 本番は `https://hikokaika.com/`。DNS、カスタムドメイン、TLS、Google OAuth設定を変更する必要はない。

## 2. Supabaseで読取確認する

SQL Editorで [check_update_readiness.sql](../supabase/check_update_readiness.sql) を実行する。SELECTだけで、秘密値やメモ本文は取得しない。

| 確認結果 | 次の操作 |
|---|---|
| `canonical_status` / `event_category` などがない | PR #8未適用の想定。0005/0006を追加で適用する必要はない |
| PR #8の列・関数がある | 適用済みとして残す。削除・巻き戻し・再実行はしない |
| `articles` / `article_companies` がない | 0007 → 0008の適用へ進む |
| このPRの0007を適用済みと確認できる | 0007を再実行せず0008のみ追加する |
| `articles`等が既にあるが適用元不明／一部だけある | **0007を再実行せず停止**。同名の既存機能や適用履歴を確認する |
| メモ3テーブルのRLSが無効／本人限定ポリシーでない | 公開前に確認が必要。今回のSQLで上書きして直したことにはしない |

このコードはPR #8のマージを前提にしない。PR #8は未マージのまま残してあり、そのまま後からマージしない。
PR #8の「公開案件には初報1件必須」は取り込んでいない。号数・日付不明・内部並び順の列が存在する場合の読取互換だけを取り込んだ。

## 3. 追加SQLを適用する

1. `0001`〜`0004`相当の既存テーブルがあることを確認する。稼働中のDBへ初期SQLを再実行しない。
2. 未適用なら [0007_tracking_articles.sql](../supabase/migrations/0007_tracking_articles.sql) **全体**をSQL Editorで一度実行し、続いて [0008_article_validation.sql](../supabase/migrations/0008_article_validation.sql) **全体**を実行する。0007適用済みなら0008のみ。BEGIN〜COMMITを分割しない。
3. エラー時はROLLBACKし、全文の成功を確認するまで新コードを本番へ出さない。0008が既存公開記事のslugを示して停止した場合は、該当記事を管理画面で修正・再承認または非公開化してから0008を再実行する。下書き保存だけでは公開版は変わらない。SQLはデータを自動修正・削除しない。
4. 読取確認SQLを再実行し、追跡情報の4列、記事2テーブル、公開・下書き用RPCと0008の検証関数が作成され、メモのRLSが維持されていることを確認する。
5. 必要に応じてSupabaseのAPIスキーマキャッシュの更新を待つ。直後の管理画面で「関数が見つからない」となる場合、適用先プロジェクトとキャッシュを確認する。

`0007`は記事本文・出典・関連会社の下書きと公開版を分ける。保存は `save_article_draft`、承認／非公開化は `set_article_publication` を使用し、管理者でもブラウザーから公開版を直接UPDATEできない。
`0008`は検証関数のみ更新する。管理APIの直接呼出しでも、不正URL、空白だけの必須項目、UTF-16単位の文字数超過を拒否する。出典URLは通常のASCIIドメインとIPv4/IPv6に対応し、国際化ドメイン（Punycodeを含む）は管理画面・DBの双方で対象外とする。日本語の出典名・URLのパスは使用できる。
既存のGoogle認証、`is_admin()`（MFA含む）、メモ・お気に入り用RLSは変更しない。`case_events.occurred_at`は日付不明を扱えるようNULLを許可する。

## 4. Cloudflareでプレビュー → 本番

- **Preview環境**: `DEPLOY_ENV=preview`、`DATA_SOURCE=sample`。検証用Supabaseを使わない場合は `PUBLIC_SUPABASE_URL` / `PUBLIC_SUPABASE_ANON_KEY` を空欄にし、本番の書き込み操作をプレビューから試さない。サンプルは架空データで、ページにnoindexを付ける。
- **Production環境**: `DEPLOY_ENV=production`、`DATA_SOURCE=supabase`、`SITE_URL=https://hikokaika.com`。既存のSupabase URL・キーを維持する。Service Role Keyには `PUBLIC_` を付けない。
- 公開データ取得で記事RPCがない場合、ビルドは失敗する。記事を黙って省略したりサンプルへ切り替えたりしない。
- SQL適用後、今回のPRをmainへマージし、既存Cloudflare Pagesのデプロイ成功を確認する。新しいサイトやSupabaseプロジェクトは作らない。
- `/admin/`のCloudflare Access保護は引き続き必須。既存設定で `/admin` と配下が保護されていることを確認する。
- 株価取得Actionはコードでcronだけを停止し、手動実行を残した。過去の価格データは残る。ニュース収集の `collect.yml` は変更していない。

## 6. 日々の運用

### 噂段階の追跡対象

管理画面「会社」→「追跡銘柄」で会社・URL・追跡理由・確認状況を入力し、公開対象として保存する。「公開処理」から再ビルドし、実際の一覧・詳細を確認する。報道イベントや記事を作る必要はない。

### 記事

「記事・調査ノート」で本文、確認できた事実、未確認事項、出典、確認日、関連銘柄を入力。下書きを保存し、プレビューで確認して公開を承認する。その後に「公開処理」で再ビルド。「このサイトへの公開反映を確認」は公開版の識別子を静的JSONと比較する（開いている環境の確認であり、プレビューから本番反映済みとは判定しない）。

公開処理の送信だけではCloudflareの成功を判定できない。Deploy Hookはno-corsなので受付の詳細もブラウザーから確認できない。Cloudflareのビルド成功と公開ページを併せて確認する。
銘柄・出来事の「公開対象」と記事の「公開版」は、ニュース収集等による別の再ビルドでも反映される。公開対象にする前に内容を確認する。
